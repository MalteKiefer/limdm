# Development

Go (version in `go.mod`), no cgo: every release binary builds with `CGO_ENABLED=0` for
linux amd64 and arm64. The only exception is the optional PKCS#11 server build.

## Build

```sh
make build                                               # dist/limdm-{server,agent}-linux-{amd64,arm64}
make build VERSION=0.16.0 UPDATE_PUBKEY=<hex>            # version and release key compiled in
make test                                                # go vet and unit tests
make lint                                                # golangci-lint v2 (.golangci.yml)
make integration DB=postgres://limdm@127.0.0.1:5432/limdm  # TestIntegration against an empty database
make snapshot                                            # goreleaser snapshot: deb, rpm, apk, Arch packages, tar.gz, no publishing
make clean                                               # removes dist/
```

`make build` builds only the server and the agent. `limdm` (the device CLI) and
`limdm-desktop` (the desktop helper) are built by goreleaser (`make snapshot`) or with
`go build ./cmd/limdm ./cmd/limdm-desktop`. An agent built without `UPDATE_PUBKEY` refuses
every self update ([operations.md](operations.md#release-key)).

### PKCS#11 build

The HSM key provider (`LIMDM_KEY_PROVIDER=pkcs11`) needs cgo and the build tag `pkcs11`:

```sh
CGO_ENABLED=1 go build -tags pkcs11 -trimpath -ldflags "-s -w" -o limdm-server ./cmd/limdm-server
```

Without the tag the provider files are left out and the server refuses `pkcs11` at start.
Details, container image and a SoftHSM test: [keys.md](keys.md#separate-build).

## Tests

| Command | Runs |
|---|---|
| `go test ./...` | unit tests; tests that need PostgreSQL or the network skip themselves |
| `LIMDM_TEST_DATABASE_URL=postgres://... go test ./internal/server` | every database test (integration, API, tenants, keys, HA, remote shell, evidence) |
| `make integration DB=postgres://...` | only `TestIntegration` |
| `LIMDM_LIVE_DNS=1 go test -run TestDoHLive ./internal/agent` | asks the real DNS over HTTPS resolvers |
| `CGO_ENABLED=1 go test -tags pkcs11 ./internal/server` | PKCS#11 key parsing tests |

The database tests drop and recreate the `public` schema of `LIMDM_TEST_DATABASE_URL`.
Never point them at a database with data. CI runs `go test -race -count=1 ./...` with a
PostgreSQL on the runner, so the database tests run there.

CI also checks `go mod tidy -diff`, `gofmt -l`, the cross compile for amd64 and arm64,
`go vet`, golangci-lint, govulncheck, `goreleaser check`, actionlint and zizmor for the
workflows, and a dependency review with a license allowlist on pull requests.

## Lint

`make lint` runs golangci-lint at the version pinned in the `Makefile` and in CI, with the
configuration in `.golangci.yml` (`nolintlint` is on: an exception is a
`//nolint:<linter> // reason` comment on the line).

## Conventions

* Validation lives in `internal/api` and runs on server and agent.
* Server texts are English keys, wrapped as `{{t "..."}}` in templates. Every such text, every
  declaration type label, audit action, command label, agent event format and literal problem
  detail needs a German entry in `deCatalog` in `internal/server/i18n.go`
  (`TestGermanCatalogComplete`) and a French, Spanish, Italian and Russian one in
  `i18n_<lang>.go` (`TestCatalogsComplete`); see [Languages](i18n.md).
* Device side texts (`limdm`, `limdm-desktop`, agent notifications and the PAM prompt) are
  English keys passed to `tr`, `trn` or `locale.T`/`locale.N`, translated in
  `internal/locale/catalog/<lang>.json`; the GTK app uses `_()` and `ngettext()` with
  `packaging/locale/<lang>.po`. `TestCatalogs` and `TestPoFiles` in `internal/locale` fail
  on a missing text, wrong plural forms or changed printf verbs. See [i18n.md](i18n.md).
* `internal/server/schema.sql` runs at every start, so every statement must be idempotent
  (`CREATE TABLE IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`, `CREATE OR REPLACE`, guarded
  constraints). The integration test applies the schema twice and fails when the second run
  fails. Data conversions that must run once go into the versioned `migrations` list in
  `internal/server/library.go` (recorded in `schema_migrations`). Migrations run in one
  transaction under an advisory lock, so several instances can start together. The schema and
  the migrations are applied only when their hash (`schemaHash`) is not in `schema_applied`
  yet, so statements in `schema.sql` must not depend on running at every start: data repairs
  and backfills over big tables belong in a migration. Indexes on tables that grow with the
  fleet go into `concurrentIndexes` (same file): they are built with `CREATE INDEX
  CONCURRENTLY` after the schema transaction, so a first build does not block writes.
  `LIMDM_TEST_EXPLAIN=1 go test -run TestExplainFleet -v ./internal/server` fills the test
  database with 50,000 devices and directory users and prints the plans of the hot queries.
* `internal/server/openapi.json` is written by hand and embedded in the server; the tests
  only check that it is valid, so update it with every admin API change.
* Commits are signed; `main` only accepts pull requests with passing checks.

## Console app

The console under `/app/` (the only console, see [console.md](console.md)) is a React app in `web/` (TypeScript strict, Vite, Tailwind 4,
TanStack Router, Query, Table and Virtual, Base UI, cmdk, ECharts modules). Exact versions
are pinned in `web/package.json` with `package-lock.json`. Node 24 or later is needed only
to change the app: its build output `internal/server/webapp/dist` is committed and embedded
with `go:embed`, so `go build`, `go install`, goreleaser and the Dockerfiles need no Node and
work air gapped. CI rebuilds the app and fails when the committed output differs.

```sh
make web                      # npm ci and build into internal/server/webapp/dist
make web-check                # lint (eslint, tsc, translations), unit tests, build with bundle budget
make web-e2e E2E_DB=postgres://limdm@127.0.0.1:5432/limdm_e2e   # Playwright: CSP and sign in
```

Inside `web/`:

| Command | Does |
|---|---|
| `npm run dev` | Vite dev server with a proxy to a local LiMDM server (below) |
| `npm run build` | type check, build, bundle budget (`scripts/budget.mjs`) |
| `npm run lint` | eslint, `tsc -b`, translation check (`scripts/i18n-check.mjs`) |
| `npm test` | Vitest unit tests (`src/**/*.test.ts(x)`) |
| `npm run e2e` | Playwright against a server it builds and starts itself |
| `npm run api` | regenerates `src/api/schema.d.ts` from `internal/server/openapi.json` |
| `npm run i18n` | keys per catalog, unused and missing keys |

The end to end tests need `LIMDM_E2E_DATABASE_URL`, a disposable PostgreSQL database (it gets
the schema, two local admins and a sealed session key in `web/test-results/e2e`). The setup
builds `limdm-server`, starts it with a throw away TLS certificate on `https://localhost:18480`
(`LIMDM_E2E_PORT` picks another port, for parallel runs in several worktrees) and signs in; `e2e/csp.spec.ts` fails on any CSP violation of any page or shared component
(`/app/dev/components` renders all of them) and checks that its detector works.

For the dev server, run the LiMDM server locally and point it at the dev server's origin
(`LIMDM_PUBLIC_URL=https://localhost:5173`, so the Origin check of the session API passes),
then start Vite with a local certificate: `LIMDM_DEV_CERT=... LIMDM_DEV_KEY=...
LIMDM_DEV_BACKEND=https://localhost:8080 npm run dev`. Sign in on the dev server's `/login`
and open `/app/`.

Rules the checks enforce:

* CSP: `default-src 'self'`, no inline script or style, no eval. zod compiles parsers with
  `new Function` unless it runs jitless, so every area imports `z` from `src/lib/zod.ts`,
  which sets that once; eslint refuses a direct `zod` import.
* Translations: German and English for every text, one catalog per area
  (`src/areas/<area>/messages.ts`) plus `src/i18n/core.ts`, French, Spanish, Italian and
  Russian in `messages.<lang>.ts` and `core.<lang>.ts`; tsc and the i18n test fail on a key
  missing in one language, the lint step on hardcoded visible text. The language follows the
  browser until the user picks one ([Languages](i18n.md)).
* Bundle budget (gzip): first load 290 KB (the shell and the core catalog; area catalogs load with their routes), a lazy
  chunk 120 KB, ECharts 220 KB, CSS 20 KB, a font 100 KB.
* Shared building blocks live in `src/components` (settings forms, blueprint picker, badges,
  downloads, data grid); an area imports another area's code only through its routes.

How the app talks to the server, the rules for the feature areas (file layout, routes,
endpoints, schemas, translations, CSP) and the checks are in
[web/CONVENTIONS.md](../web/CONVENTIONS.md). The API it uses is in
[admin-api.md](admin-api.md#console-app).

## xterm.js

The console terminal of the remote shell uses xterm.js with the fit and canvas addons,
vendored into `internal/server/web/static/vendor/xterm` and embedded in the server binary.
Without these files the session page shows that the terminal files are missing.

```sh
scripts/vendor-xterm.sh
```

The script needs `npm`, fetches the exact versions pinned in it from the npm registry
(integrity checked by npm), and writes `SHA256SUMS`. Later runs refuse files that differ
from that file. Commit the directory. To update, change the versions in the script, delete
`SHA256SUMS`, run it and review the diff.

## Swagger UI

The API reference at `/api/v1/docs` runs Swagger UI (`swagger-ui-dist`, Apache 2.0),
vendored into `internal/server/web/static/vendor/swagger-ui` (bundle, stylesheet, `LICENSE`,
`NOTICE`, `VERSION`, `SHA256SUMS`). The page itself is `internal/server/apidocs.html`, its
initializer and LiMDM styles are in `internal/server/web/static/apidocs`.

```sh
scripts/vendor-swagger-ui.sh
```

It works like the xterm.js script: exact version pinned in the script, refuses files that
differ from `SHA256SUMS`. Pick a release at least two weeks old. After changing
`openapi.json`, run `npm run api` in `web` to regenerate `src/api/schema.d.ts`;
`TestOpenAPIOperations` requires a declared tag, a summary, a security list and a unique
operation id on every operation.

## Release

Requirements in the GitHub repository, both in the protected `release` environment:

| Name | Kind | Content |
|---|---|---|
| `UPDATE_PUBKEY` | variable | public release key printed by `limdm-server keygen -out release.key` |
| `RELEASE_SIGNING_KEY` | secret | content of `release.key` |

The workflow fails when either is missing. See [operations.md](operations.md#release-key).

1. Merge to `main`.
2. `git tag -s vX.Y.Z -m "LiMDM vX.Y.Z" && git push origin vX.Y.Z`
3. Approve the `release` environment in GitHub Actions.

The workflow runs goreleaser (packages, archives, SBOMs, checksums, the server image
`ghcr.io/maltekiefer/limdm-server`), signs `SHA256SUMS` with
`limdm-server sign -key-env RELEASE_SIGNING_KEY` and uploads `SHA256SUMS.sig`, and attests
build provenance for packages, archives, checksums, `scripts/install-agent.sh` and the
image.
